# Soak test, 2026-11-09

> Status: done for this round. Branch `soak-2026-11-09`. Harness: `packages/soak`.
> Verified = seen in a soak run or a test. Inferred = reasoned from code, not run.

## What ran

`packages/soak/src/run.ts` starts the real main process (`bun packages/cli/src/main.ts up
--headless`, scratch `DUCTER_DATA_DIR` and `HOME`, `DUCTER_SCRIPTED_MODEL=1`,
`DUCTER_MEMORY=off`, `DUCTER_PUSH=off`, a fake `nmem` on `PATH`), pairs a real local
`ducter worker`, and drives everything over the real WebSocket with three clients: a driver,
a watcher that reconnects with its cursor, and one that reconnects fresh.

- **Work:** tasks in three scratch git repos (commit, ask, block, fail, never-report, slow up to
  60 s, about one in eight on the worker), chats, `wait_until` timers (5–120 s), partner `ask`
  decisions with short defaults, task questions answered go / hold / reply or left to their
  default (`DUCTER_DECISION_DEFAULT_MS=25000`), direct `task_send` (steer when working,
  a new turn when idle), partner `task_send`, interrupts, drops, undrops, reopens, merges, read
  receipts, `task_history`.
- **Chaos:** SIGKILL the main every 40–110 s, aimed mid-turn, mid-decision (kill 0–25 ms after a
  `decide`), mid-merge (0–80 ms after a merge), mid-partner-turn (0–400 ms after a message) or
  at random; restart after 0.3–3 s. SIGKILL the worker every 2.5–5 min, back after a blip
  (2–8 s) or past the 20 s grace (25–60 s). Idle parking at 90 s (`DUCTER_PARK_IDLE_MS`).
- **Rest:** the last 8 minutes add no work and no chaos; the run waits until nothing is working,
  hot, or due, then checks, then does a clean restart and checks that it changes nothing.

The scripted model (`packages/cli/src/scripted-soak.ts`) understands `#soak` lines, so the
partner and tasks act out each case through Ducter's real MCP tools. No model, no cost.

### Checks

Live, per WebSocket connection: the replay is channel-only and not past the welcome head; live
events arrive with seq exactly head+1, head+2, … (no gap, no repeat); every event a client was
shown is in the Log, byte-identical; one `action_result` per `task_action`.

Every 2 minutes and at rest, over `ducter.db` (`packages/soak/src/invariants.ts`, unit-tested):

| Invariant | How |
|---|---|
| Log seqs gapless, monotonic across restarts | 1..N, head never goes back |
| No lost or doubled user message | one `user_msg` per clientId; each echoed send is in the Log; each soak command has exactly one effect (reply, task or refusal, timer, question) |
| Decision answers durable and exactly once | ≤ 1 resolution per decision; every answer a client saw echoed is in the Log; every due reversible default applied |
| Go / Reply reaches its task exactly once | the forward text appears once in the task's input after the question |
| Waiters fire exactly once, never early, never missed | one armed and ≤ 1 terminal state each; fired ≥ `at`; the partner answers each soak timer once |
| No doubled ack or result | ack jobIds unique; one `job_status` per (job, state); one task per job |
| Truthful rest | nothing working or queued, nothing hot; needs_you only with an open question |
| Living message agrees | the open one asks no answered question and shows no state the card lacks; every open question is in it |
| On hand agrees with the Log | a fresh client's On hand equals core's registry rebuilt from the Log |
| Merges | what was reported merged is in `main`; no `MERGE_HEAD`, no `index.lock`, no dirty checkout, no prunable worktree |
| Worktrees kept per design | every repo task that started has its worktree (no archiving yet) |
| Quiet restart | a clean restart at rest adds nothing but parking and shutdown lines |
| Resources | RSS, open FDs, children and descendants of the main every 15 s (`metrics.csv`) |
| No orphans | nothing left running from the data dirs after shutdown |

## Bugs found and fixed

Each one has a deterministic regression test that fails without the fix.

1. **A worker on the same machine (or behind an SSH tunnel) could never join.** A loopback
   request was classed "local" before its token was read, so `/worker` answered 403 and the
   worker retried forever. Fixed in `core/src/auth.ts`; test in `core/test/workers.test.ts`.
   *Verified* (soak t1: the worker reconnected for the whole run).
2. **Every task kept its harness process forever.** There was no warm → parked transition: OAR
   keeps one `claude` process per session, so each task that ever ran held a process (hundreds
   of MB) until the main restarted. Idle sessions with a known id are now closed after
   `DUCTER_PARK_IDLE_MS` (default 15 min, focus-window-states) and resumed by id on the next
   input. `runner/src/runner.ts`; tests in `runner/test/runner.test.ts`. *Inferred* for real
   harnesses (scripted sessions run in-process); *verified* that parking and resuming hold up
   under the soak (about 400 park transitions per 50-minute run, no stuck task).
3. **A restart mid-turn doubled one message and dropped another.** Two user messages shared a
   partner turn; the turn opened the first one's task and the process died. On restart the
   first was queued again (its ack carried the second one's seq) and its task opened twice,
   while the second counted as answered and was never handled. The turn in flight is now kept
   in `partner/state.json`; after a restart all its triggers run again as one turn, with a
   line saying what already happened, and `task_open` / `wait_until` / `ask` / repeated lines
   from the cut-off turn are handed back instead of done twice. `partner/src/partner.ts`; test
   "restart mid-turn with two messages in one turn". *Verified* by test; the soak's
   mid-partner-turn kills then showed no doubles.
4. **A kill inside `task_open` doubled the task.** SIGKILL after the runner logged `task_open`
   and before the partner logged its job: the task still started after the restart, and the
   redone turn opened a second one (soak r1, `user_msg.doubled`). The carried-over turn now
   counts tasks by `task_open` too and binds the handed-back task to its ack. Test "restart
   inside task_open". *Verified.*
5. **Answering a dropped task's question brought it back to life.** Drop, then Go on its still
   open question: the card flipped to `working` (the forward failed), and the next restart
   resumed and ran the dropped task (no-chaos run, `forward.lost` + `rest.stuck`). Now
   answering is refused with "That task was dropped. Undo the drop first, then answer.", its
   default doesn't fire, a resolution that lands anyway changes nothing, and `task_send` to a
   dropped task is refused before it can answer the question. The question stays open, so
   Undo brings the task back exactly as it was. `core/src/decisions.ts`, `core/src/ws.ts`;
   test in `core/test/flow.test.ts`. *Verified.*
6. **Scripted demo model opened tasks nobody asked for.** Any partner input that mentioned
   "task" (e.g. a `[decision resolved] (task …)` line) opened a task titled with rendered
   context. Demo-only, but it would confuse a first-run demo. `cli/src/scripted.ts`; test
   `cli/test/scripted.test.ts`.

Also added: `DUCTER_DECISION_DEFAULT_MS` (reversible default delay; demos and soak use seconds).

## Needs a design call

1. **A task that stops without reporting is silently "working" forever.** The runner nudges
   once, then logs "stall rule" and leaves the card `working`. The design says C then notifies
   M (focus-window-states, stall rule); that notice isn't built, so neither the partner nor the
   user hears anything, and every restart resumes the task and pays two more turns. Proposal:
   after the nudge, C appends a system `report {state:"blocked", summary: "stopped without a
   report"}` so the card reads Waiting with a reason and the partner is woken (a trigger).
   Tradeoff: it moves attention, which the current rule says not to; alternative: a new
   trigger kind that wakes the partner without moving the card (protocol change).
2. **A message sent just before a crash has no receipt.** `send` has no ack; a client knows a
   message is safe only when its `user_msg` echo arrives. The soak's client resends any
   unechoed message or answer on reconnect if it isn't in the replay (answers were resent 3
   times in the final run, never doubled; no message happened to be caught in flight). Proposal: core dedupes `send` by clientId, and the clients resend
   unechoed messages on reconnect. Check what desktop and web do today.
3. **`action_result` can be lost with the socket.** Two merges / actions in r1 got no result
   because the main died mid-action. The action may or may not have happened; a client should
   show "not sure, check" and re-read the card, not assume failure.
4. **A dropped task's question stays open with no default.** Now safe (fix 5), but after Undo
   its default timer isn't re-armed: it waits for the user. Fine for now; re-arm on Undo if it
   matters.
5. **Doctor runs on every headless `up` until something signs in**, which adds about a second
   to every restart. Harmless; noted.
