**一、先选对 libc 目标（最常见的坑）**
- 默认的 `bun-linux-x64` / `bun-linux-arm64` 指 glibc 版本。
- 要跑在 Alpine 或其他 musl 系统上，用 `bun-linux-x64-musl` / `bun-linux-arm64-musl`。
- 二进制是动态链接 libc 的，跨发行版、跨版本不保证能跑。官方文档没写最低 glibc 版本，部署前在目标系统上实测。
- Alpine 上如果报找不到 C++ 运行库，文档里的做法是 `apk add libstdc++ libgcc`。

**二、交叉编译**
- 用 `--target` 指定目标系统、架构或 Bun 版本。
- 默认架构是 x64。给 Graviton 或树莓派编译要显式写 `bun-linux-arm64`。
- 交叉编译时 Windows 元数据选项不能用（`hideConsole` 除外）。
- `--target=node` 和 `--target=browser` 不支持。`--outdir` 换成 `outfile`。

**三、CPU 后缀**
- `-baseline` 和 `-modern` 后缀仍可用，但与不加后缀的版本生成同一个二进制，它在运行时自动选择 CPU 代码路径。老文章让你二选一的，可以忽略。

**四、运行时读取的文件**
- 运行时会从当前工作目录读取 `.env` 和 `bunfig.toml`，默认开启。在生产环境要确定性行为，用 `--no-compile-autoload-dotenv` 和 `--no-compile-autoload-bunfig`。文档说以后版本可能默认关掉。
- `tsconfig.json` 和 `package.json` 默认不加载，需要 `--compile-autoload-tsconfig` 或 `--compile-autoload-package-json` 才开。

**五、路径与文件**
- 嵌入的文件在 `/$bunfs/root/...` 下，只读，写入会报 `EROFS`。
- `__dirname` 和 `__filename` 保留的是编译机器上的源码路径。
- 嵌入的资源可以通过 `import.meta.dir` 访问。
- 没嵌入的相对路径，按进程当前工作目录从磁盘读取。SQLite 数据库同理，除非也嵌入了。
- 文档没写 `process.execPath` 的行为，别假设。

**六、原生模块**
- 用 `@mapbox/node-pre-gyp` 之类的工具，直接 `require` 那个 `.node` 文件，否则打包不对。
- 像 `sharp` 那样依赖同目录共享库（如 libvips）的，要用 `--aot` 加 `--asset` 把整个目录嵌进去。

**七、其他**
- Worker 入口要在构建时手动列出，Bun 不会自动检测。
- `--trim` 会删掉 `bun` 命令行，所以 `BUN_BE_BUN=1` 在裁剪过的可执行文件里不工作。
- `--aot` 和 `--trim` 官方标为实验性。
- 二进制体积还很大，文档自己也承认。1.4 说 Linux 上 Bun 本身最多小 17%。

**八、1.4 相关，但未被官方证实**
- 有第三方文章提到 1.4 发布当天有个报告：`--compile` 生成的二进制在运行用户代码前就被 SIGKILL。它在 macOS 下，我没能在 GitHub 上核实。
- 另一个报告是 Claude Code 随包附带的 Linux x64 基线版二进制（基于 Bun 1.4.0）在 glibc 2.41 的 Debian 13 上启动即 segfault。这不是 `--compile` 产物，但说明 1.4.0 的基线构建在 Linux 上出过问题，已标为解决。
- 文章还说 1.4 把最低 glibc 要求从 2.26 降到 2.17，这一条也没有官方来源。

**建议**：用 1.4 的 `--compile` 做产物时，先在目标发行版（包括最老的那个）上跑一遍冒烟测试，再决定用 glibc 还是 musl 目标。
