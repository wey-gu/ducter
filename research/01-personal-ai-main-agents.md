## 1. DimAgent ("dim agent")

Evidence comes from the plugin HANDOFF (`dim-ext/docs/HANDOFF.md:20-40`), the plugin README, the dimagent.com landing page, and GitHub issues #16 and #22 on archships/dimcode.

1. **Session model.** Thread-based: the sidebar has "New thread" and one thread per task (landing page, V). Local state lives in `~/.dimcode/v2/dimcode.sqlite` (V, HANDOFF §2.1). Each main session is a long agent session with compaction. Issue #22 is "long session 400 over limit, no auto-compaction record", and the maintainer's answer is that a custom model id's config prevented the normal compaction trigger (V). So compaction is threshold-driven from per-model config.
2. **Prompt cache.** Issue #16 (V, user report with billing data) is a cautionary tale. In one long gpt-6-astra session, two request "shapes" alternated, and they differed by about 8.4–8.7k tokens **at the front of the request**. One shape always had `cache_read=0`, even on the system prompt. Fork sessions also had 0% hits. The trigger correlated with `wait` timeouts on slow subagents. The maintainer's reply is "probably the provider's 5-minute cache expired during long waits." No re-warm or expire-awareness is evident (I).
3. **Respond-first and async.** The `background_tasks` table has `toolName ∈ {agent, exec, schedule_wakeup}` (V, HANDOFF:29). The main agent calls `agent create_external` (V, hooks.test.js:443). The task runs asynchronously in a CLI spawned by the desktop main process, and the main agent can `wait`. Results come back as **`<notification>` injected messages** (V, issue #16 text) and the main agent can be steered.
4. **What the main agent sees of subagents.** Only `status` plus a `completion` field, which is a **final-result summary**. "agent 任务 outputPath 为空；completion 仅为最终结果摘要——过程不落盘" ("agent tasks have an empty outputPath; completion holds only the final-result summary; the process is not persisted") (V, HANDOFF:31). The full trace exists only in the external harness's own store (`~/.codex/sessions`, `~/.kimi-code/sessions/.../wire.jsonl`, `~/.pi/agent/sessions/*.jsonl`). The plugin exists because users wanted the transcript on demand. `metadata` holds `subagentType/externalAgentType`, `childSessionId`, `taskTitle`, `agentName` (the dim agent gives each worker a human name, e.g. 林澈), `subagentInput.prompt`, and the model (V).
5. **Identity and memory.** Not documented.
6. **Long-running work.** `schedule_wakeup` is a first-class background-task type (V). The UI has "Scheduled tasks" (V). The landing page claims a loop "until the target is approached" (V, marketing).
7. **Clever / avoid.** Clever: it uses external harnesses as workers and names them, which is close to Ducter's Focus Windows. Avoid: (a) a completion that is a summary only, with no pointer to the transcript (the plugin had to reverse-engineer 6 harness store formats); (b) variant prefixes for different call types, the cache-killer in #16; (c) blocking `wait` that outlives the provider cache TTL.

## 2. xAI Grok Bot (product) and grok-build (open harness)

### 2a. Grok Bot (docs.x.ai/grok-bot: how-grok-bot-works, bots, faq)
1. **Session model.** "Each Bot has its own conversation." Reset "starts the history over but keeps the Bot's memory, files, routines, and settings" (V, /bots). So there is one long conversation per Bot plus durable memory, i.e. a persona-per-session design. Voice chats "draw on earlier calls and your recent chat" (V).
2. **Prompt cache.** Undocumented.
3. **Background work.** "Closing the app, laptop, or phone does not stop a background turn or routine" (V, FAQ). "When background work finishes, you get a notification" (V). The chat "shows each step as the Bot works" and the reply is "a summary of everything it did" (V).
4. **Delegation.** "Your primary Bot is your main contact. It checks in on its own and coordinates work with your other Bots, and it can pass work to a specialist Bot" (V). Bots pass context "through direct messages, group chats, and shared files", and all Bots share one VM (separate screens, shared browser logins) (V). Delegation is peer-to-peer between persistent Bots, not ephemeral subagents.
5. **Identity and memory.** Memory is per Bot: "preferences, rules, and a dated work log". A few facts (name, timezone) are shared across all Bots. "A Bot decides on its own what to remember." There is no memory UI; you ask "What do you remember about me?" Memory "isn't a source of truth": recheck current data (V). Personas are set **by chat**, with no settings page for personal Bots (V).
6. **Loops.** A skill is a saved procedure. A routine assigns a skill to one Bot "on a schedule or ... after an event" (Slack message, email to the Bot) (V). Approvals from unattended work **expire after ~30 min**, while approvals in a live chat wait (V, FAQ).
7. **Notable.** "Only your own messages count as instructions. Page content does not" (V). Avoid: no memory inspection or export (3P vellum.ai criticism), and Bots are not a security boundary.

### 2b. grok-build source (xai-org/grok-build, Rust, ~77 crates). The main-agent machinery is here.
- **Typed synthetic-message taxonomy.** Every injected user or system item carries a `SyntheticReason` (`crates/codegen/xai-grok-sampling-types/src/conversation.rs:100-190`, V): `Human, Primary, CompactionMeta, SystemReminder, LengthContinue, ProjectInstructions, AutoContinue, AutoRecovery, Interjection` (mid-turn steer "injected between tool batches ... without canceling the turn"), `AgentMessage, TaskCompleted` ("auto-wake synthetic prompt ... wakes the agent for a new turn"), `SubagentCompleted, NotificationDrain` ("idle-gated ... batched monitor events and/or bash task completions drained when the session is idle"), `GoalSummary, GoalClassifierNudge, SchedulerFired` (`/loop`), `StopHookFeedback, ParentHumanMessage, SessionPrefix, Unknown`. `starts_prompt_turn()` separates wake-ups that open a new turn from mid-turn injections, and unknown reasons fail safe as turn boundaries.
- **Cache invariants.** `ProjectInstructions`: "once placed, never replaced (replacing it would bust the KV-cache prefix)" (conversation.rs:121, V). There is a `prompt_cache_key` sticky routing key (conversation.rs:661), and a test asserts the key actually reaches the wire, because "a key that never reaches the wire looks like a 0% cache hit, not a bug" (conversation.rs:2265, V).
- **Cache-aligned side calls.** `/btw` (side question), recap, and title refresh reuse the **parent's exact prefix**: the same tools ("they serialize into the cached prefix"), the same reasoning effort ("dropping it here would share no prefix with the main turn"), and preserved reasoning items, with only a suffix appended. Tools are attached but never executed (`xai-grok-shell/src/session/acp_session_impl/side_call.rs:104-133`, `recap.rs:245-263`, V). Cache read and write rates are logged per aux call (side_call.rs:8-60).
- **Prefire two-pass compaction.** At `threshold - 10%`, pass 1 runs **in the background** and summarizes about 95% of history into NOTE₁. It is keyed by a fingerprint of the prefix, and an edit, rewind, or branch invalidates it. At the threshold, a blocking pass 2 only rewrites NOTE₁ plus the ~5% tail (`session/two_pass.rs:1-12`, `session/compaction.rs:59-90,180`, V).
- **Post-compaction state rehydration.** After compaction a `<system-reminder>` re-injects the live state: Running Background Tasks, Running Subagents, Scheduled Loops (with next fire time), Running Workflows, TODO List, Files Edited, Available Skills and Workflows, Connected MCP Servers (`session/helpers/compaction_context.rs:123-640`, V).
- Feature list per 3P (dailyaiworld, pyshine): parallel child sessions (up to 8, each in its own git worktree), save/load/resume/rewind/compact/fork sessions, and ACP leader/follower.

## 3. OpenAI dots (learn.chatgpt.com/docs/dots/*, flaviocopes.com/openai-dots)

1. **Session model.** One dot, many channels: ChatGPT, voice, Slack, Teams, and SMS (beta). "Messages stay in their own channel, but the dot can use context across channels." Switching channels "doesn't create a new dot or reset its memory" (V, /dots, /dots/channels). Per-turn context is assembled: "Context for an interaction is **a selection** of this information, so it can differ from what a background task sees. Calls use selected conversation context" (V, /tasks-and-memory). The dot "can search past ChatGPT conversations"; "retrieved content isn't the same as persistent memory" (V). This is reconstruction per interaction, not one raw long session (I: the visible channel threads are views, and the model context is a curated selection).
2. **Prompt cache.** Not documented.
3. **Respond-first.** "It can use background agents to handle several tasks in parallel **while you keep chatting**." Background agents "run in parallel and report back to the dot" (V). On a voice call you can type, and "assigned work can continue after the call ends" (V). The **main task** is distinct from delegated tasks: "Pause stops your dot's current main task. It doesn't stop delegated tasks or cancel future scheduled runs" (V, /controls).
4. **Delegation.** The dot creates **real Codex / ChatGPT Work tasks**: "start new cloud threads, create Work or Codex tasks on a connected computer, and continue existing local Codex tasks", and "send follow-up instructions to tasks it created and check their results" (V). Each task "has its own conversation and doesn't automatically receive all your past conversations"; it gets "instructions and context from the dot for that work" (V). Cloud threads "appear as separate conversations" that the user can steer directly (V). "A completed run doesn't by itself confirm that the requested result was achieved or delivered" (V): the dot is expected to verify. OpenAI testing (3P quoting docs) found "moderate scope violations rose from 8.6% with five intervening tasks to 19.7% with ten", which is evidence that piling unrelated work into one main context degrades it.
5. **Identity and memory.** Name, avatar, and handle `@name-dot`; "introduces itself" on first contact (V). Memory has three layers: the conversation, ChatGPT memory (two-way sync), and the dot's **own notes** "about your preferences, decisions, and ongoing work". These are "not a complete transcript" and are updated as decisions change (V). Notes can't be edited individually; deleting the dot is the only way to clear them (3P flaviocopes).
6. **Loops and waits.** "It decides when to pause and resume work, so a fixed schedule isn't required": it can **self-schedule wake-ups**, e.g. to recheck an email reply (V). Fixed schedules are explicit objects (what to check, time zone, end date, which changes merit notification, delivery destination) shown under **Scheduled**. They are kept separate from **Activity** (delegated tasks) (V). Event triggers apply only when a service supports events: "Connecting Slack ... alone doesn't create a monitoring task" (V). "Proactive research" background agents are **read-only** and keep private notes (V).
7. **Clever.** Per-update-type **routing** ("routine progress in ChatGPT and decisions in Slack, urgent by text") (V). There are three distinct ledgers: main task, Activity (delegations), and Scheduled. Disclosure check: before sharing private-channel info with others, it asks (V).

## 4. Meta Muse and Muse Spaces

Sources: about.fb.com/news/2026/09/introducing-muse (V, marketing-level); vellum.ai/blog/official-muse-breakdown (3P, competitor); arXiv 2610.08699 nanoMuse (3P with leaked-prompt claims); kingy.ai / i-scoop on Spaces (3P).

1. **Session model.** "Message it just like messaging another person, in the Muse app or directly in WhatsApp" (V). No public detail on sessions or compaction. A Muse prompt copy that nanoMuse's authors read (unverifiable) says the VM "is replaced about hourly while the home directory persists" and that "tools load on demand in namespaces". nanoMuse itself syncs "the main conversation by default and side chats on request", which is again the main-plus-side-threads shape.
2. **Prompt cache.** Nothing public.
3. **Background work.** "Keeps working after people close the app, and comes back **when something changes or when it needs approval**" (V). It "reports back only when meaningful milestones are reached or when human confirmation is required" (3P vellum). So the design is milestone-gated push and explicitly not chatty.
4. **Delegation.** Muse "formulate[s] a plan, launch[es] subagents" (3P). The VM runs "concurrent sub-agents" and cron jobs. A browser subagent works from accessibility-tree snapshots (3P). The leaked prompt says "spawn sub-agents one level deep" (nanoMuse, unverified).
5. **Identity and memory.** It "remembers what matters", supports "forget", and keeps durable state in PostgreSQL outside the agent runtime cell, with files kept in the VM (3P). Per nanoMuse's leaked-prompt reading, background jobs "maintain memory, generate ideas, advance goals and write the Feed" (unverified). nanoMuse's own design uses SOUL.md / USER.md / GLOBAL.md / a dated diary / HEARTBEAT.md, copied from OpenClaw conventions.
6. **Spaces (2026-11-06).** A Space is an agent-built persistent mini-app (tracker, planner, board, dashboard) that you revisit. It "can occupy the sidebar or main tabs" and **refreshes in the background from connected apps without re-prompting** (3P). Sharing isn't supported yet. (I) Spaces are durable, structured *outputs* of the agent, separate from the conversation stream. That is the same "collapse detail out of the main channel" move Ducter wants, applied to artifacts.
7. **Security model.** **Sentinel** is a separate agent that is system-level separated from Muse. "Nothing Muse does reaches the internet unless the Sentinel approves it." Credentials are usable but invisible to the agent (V, about.fb.com).

## 5. OpenClaw (open source): the most detailed public "main session" design

All paths below are relative to `openclaw/docs/`.

1. **Session model** (`concepts/main-session.md`, V). "Every direct message ... lands in **one rolling conversation**: the main session" (line 12), keyed `agent:<id>:main`. "Heartbeats wake it, background work reports back to it, and activity elsewhere flows up to it" (line 20). Group or room sessions stay **isolated but watched**: "Activity queues up as compact notices — coalesced per conversation, never one wake-up per message", consumed on the next turn or heartbeat (line 69). New-session creation drops a bounded notice into Home "without triggering an extra wake-up". This is very close to Ducter's channel-plus-collapsed-threads idea, except OpenClaw's Home *is* a raw long session with compaction.
2. **Context assembly and cache prefix** (`concepts/system-prompt.md`, V).
   - There is an explicit **internal prompt-cache boundary**. Stable content (project context, workspace/persona files, fixed policy) sits *above* it. Tool catalogs, skills, memory recall, channel and per-turn guidance sit *below* it, so "refreshing a catalog or changing granted tools leaves the cached workspace prefix byte-identical" (line 63).
   - On Anthropic and OpenAI Responses routes "the embedded session pins both sides of this boundary. Refreshed sections are **appended as instruction messages after the current user turn**, preserving earlier prompt and history bytes" (line 71).
   - Date/time, active exec sessions, and active subagents travel in a separate per-turn **Runtime Context message**, "so day rollover leaves the complete system prompt and prior conversation bytes unchanged" (lines 49, 212). Retained per-turn messages persist so the next request extends the prefix (line 214).
   - Subagent sessions only inject `AGENTS.md`, not SOUL/USER/MEMORY (line 202). The persona never reaches workers.
3. **Expire-aware pruning** (`concepts/session-pruning.md`, V). This is the closest existing analogue to Ducter's expire-aware resume. `contextPruning.mode: "cache-ttl"` means old tool results are only soft-trimmed or hard-cleared **after the provider cache TTL has elapsed** ("Before the TTL elapses, no new pruning occurs", line 73). The TTL clock is refreshed on every successful request. Anthropic defaults are 1h TTL, and the proactive-check cadence is seeded at 1h (OAuth) or 30m (API key), i.e. aligned to the TTL. Pruned views are stored as **projections** (delta-logged, checkpointed) so the *same pruned bytes replay* afterwards and across restarts. "Clearing invalidates the prompt cache from the first cleared result; `clear_at_least` prevents a clearing event that would remove too few tokens to justify the new cache write" (line 59). Never prune the last 3 assistant turns or anything before the first user message (bootstrap reads) (line 100). Images are not age-cleaned because "replacing an already-sent image ... discards the provider's cached context" (line 109).
4. **Compaction** (`concepts/compaction.md`, V). It triggers at min(75% of window, window − reserve). The summarizer input is budgeted: newest messages verbatim (½), older *user* messages, "which carry the asks, decisions and corrections" (¼), oldest messages (1/10), and sampled runs. A "safeguard" mode audits pending asks and exact identifiers. "Recovery keeps a bounded copy of the active human request in the summary" across repeated compactions (line 29). It flushes memory before compacting (line 142). History hydration advances its window "in quarter-cap steps ... **Its existing prefix stays unchanged between steps**", and "Chunking trades some immediate history for prefix-cache reuse" (lines 324-332). That is a cache-stable sliding window.
5. **Respond-first, steering, async re-entry** (V).
   - Queue modes are `steer` (default), `followup`, `collect`, and `interrupt`. A steer is appended after the current tool batch. Unstarted sequential calls get the synthetic result "Skipped to process an incoming message." (`concepts/queue-steering.md:19-30`).
   - Subagents (`tools/subagents.md`, `tools/subagents/announce.md`): `sessions_spawn` runs in its own session. The default context is fresh; `context: "fork"` is used "when a child genuinely needs the requester's current transcript". Completion is **push-based**. For top-level requesters it arrives as "a follow-up agent call" (a new turn); for nested orchestrators it is an internal injection (announce.md:28-29). With `completionTarget: "parent"` the result is reviewed in a private parent turn that "may finish silently" (`NO_REPLY`). The announce payload is the child's result plus a **stats line** (runtime, tokens, cost) and `sessionKey/sessionId/transcript path`, so the parent can pull the full transcript with `sessions_history` (paged, 4000 chars per block, 80KB cap) (announce.md:247-274). The result goes in the context and the transcript stays one tool call away.
   - `sessions_yield` ends the requester's turn while children run. A registry owns the "settlement batch" and starts **one successor turn after the children settle**: "Individual announcements must not start a competing continuation" (`concepts/subagent-yield-handoff.md`).
   - Progress drafts: one channel message is edited live as a status checklist, then the final answer is delivered (`concepts/progress-drafts.md`).
6. **Loops and scheduling** (V). Automations (cron) target `main` (the job runs through the main session queue with its context), `isolated` (a fresh session), or `session:<key>`. To "come back to this conversation later (e.g. recheck CI)", the agent schedules a one-shot `at` job with an `agentTurn` payload into its own session (`automation/cron-jobs/payloads.md:501-507`). Heartbeat monitors were *retired into ordinary jobs* (`gateway/heartbeat.md`). **Standing intents** are event-conditioned prospective memory ("when X is mentioned, do Y"), stored in SQLite and checked before replies (`concepts/standing-intents.md`). Dreaming does background memory consolidation (light/deep/REM phases) (`concepts/dreaming.md`).
7. **Pluggable context engine** (`concepts/context-engine.md`, V). The interface is `ingest / assemble / compact / afterTurn / prepareSubagentSpawn / onSubagentEnded`. For persistent backend threads (the Codex app-server harness) there is `contextProjection: {mode: "thread_bootstrap", epoch}`: "inject the assembled context once per epoch and reuse the backend thread until the epoch changes, instead of re-projecting every turn" (line 359). This is exactly the problem of driving an off-the-shelf harness as the main loop. Codex keeps its native compactor; OpenClaw mirrors the transcript and seeds fresh native threads with bounded history plus a summary (`plugins/codex-harness-runtime/compaction.md`).
8. **Identity and memory** (V). Workspace files are SOUL.md (persona), IDENTITY.md, USER.md, AGENTS.md, MEMORY.md (curated, injected each session), and `memory/YYYY-MM-DD.md` (daily, retrieved on demand). Bootstrap caps are 20k chars per file and 60k total. On `/new`, the tail of the conversation is saved to daily notes and recent notes are re-primed.

## 6. Letta / letta-code (open source)

- **Model** (V, README and docs.letta.com). One stateful agent has many conversations. Memory is a **git-backed "MemFS"** shared across conversations. Resume fetches a *bounded tail* of the exact conversation (`docs/plans/resume-tail-fast-path.md`).
- **Sleep-time / dreaming** (V, docs.letta.com/guides/agents/architectures/sleeptime). Background subagents review recent conversations and update memory "without interrupting your active work". They trigger **after N agent steps or when the context window is compacted**, with an optional second background review conversation.
- **Cache-relevant detail** (V, source). The memory worker runs "inside the existing background task, never awaited by the primary". It works in a memory **git worktree**, merges, and then calls `recompileAgentSystemPrompt(conversationId)` so "server-side prompt state picks up the latest memory content" (`src/agent/memory-worker.ts:60-90`, `src/agent/modify.ts:692-735`, `src/agent/memory-worktree.ts:241`). Recompiles are coalesced per conversation (`src/headless.ts:3243`). (I) Memory lives *in the system prompt*, so every merged memory change rewrites the very front of the prefix: a full cache miss for that conversation. That is the MemGPT design cost.

## 7. Cross-cutting answers

| Question | Dominant pattern observed |
|---|---|
| Session model | Hosted products (dots, Grok Bot, Muse) present **one persistent agent identity** and keep per-channel or per-Bot visible histories, but the model context is a *selection* (dots) or a long session plus memory (Grok Bot). The open source projects (OpenClaw, DimAgent) use **one rolling raw session with compaction**. Nobody publicly does Ducter's "rebuild from a channel cut point". |
| Cache awareness | Only the open harnesses show it: OpenClaw (cache boundary, runtime-context carrier, TTL-gated pruning, projection replay, chunked windows) and grok-build (never-replace invariants, cache-key wire test, prefix-sharing side calls, prefire compaction). DimAgent shows what happens without it (#16). |
| Respond-first | Universal: chat continues while background agents run (dots, Grok Bot, OpenClaw steer queue, grok-build Interjection). |
| Async re-entry | A synthetic message that **starts a new turn** (grok-build `TaskCompleted/SubagentCompleted/SchedulerFired`, OpenClaw follow-up agent call, DimAgent `<notification>`), with **idle-gated batching** (grok-build `NotificationDrain`, OpenClaw coalesced notices and settlement batches). |
| Subagent visibility | Summary or result in context, plus a handle to the full transcript (OpenClaw stats line plus `sessions_history`). dots shows Codex threads as separate, user-steerable conversations. DimAgent has summary only, and users complained. |
| Memory | Curated persona/user files plus agent-written notes ("not a transcript") plus searchable episodic logs. Background consolidation (OpenClaw dreaming, Letta sleeptime, Muse jobs). Memory is "not a source of truth" (Grok Bot). |
| Loops | Three distinct primitives: self-scheduled wake-up into the *same* session (dots, OpenClaw `at` → `session:<key>`, DimAgent `schedule_wakeup`); recurring schedules (separate ledger); event triggers that must be explicitly created ("adding to a channel ≠ monitoring"). Standing intents are a fourth primitive (OpenClaw). |

## 8. Implications for Ducter

**Session and prefix engineering**
1. **Adopt an explicit two-zone prompt with a hard cache boundary** (OpenClaw system-prompt.md:63-71). Persona, user, and stable policy go above it; tool catalogs, skills, and channel state go below. Deliver changes as *appended instruction messages after the current turn*, never by editing earlier bytes. Put time, date, and live subagent/task status in a per-turn **runtime-context message**, never in the system prompt.
2. **Do not put mutable memory in the system prefix** (the Letta recompile cost). Persona and memory snapshots are frozen per "epoch" (one cut-point rebuild). Memory written mid-epoch is surfaced as appended notes, and folds into the prefix only at the next rebuild.
3. **Expire-aware resume should be TTL-gated, like OpenClaw's pruning.** Track last-successful-request time per session. While warm, never rewrite (append only). Once the TTL has elapsed, a rewrite is free, so do all destructive work then: re-cut from a channel point, collapse threads, clear tool results. OpenClaw's `clear_at_least` logic carries over: rebuild only if the token saving justifies the cache write.
4. **Persist the rebuilt view as a projection** (OpenClaw delta-logged projections). After a rebuild, the exact bytes must replay identically across restarts and tool loops. Keep the raw channel log separate from the projected model context.
5. **Precompute the cut-point summary in the background** (grok-build prefire two-pass). Keep a rolling, fingerprinted summary of the "main channel up to cut N", ready before the cache expires, so expire-aware resume has a blocking cost of only the short tail.
6. **Use one byte-identical prefix for every call type on the main session.** That covers turns, wait polls, notification turns, and side questions: the same tools, effort, and reasoning settings. DimAgent #16 shows alternating front-variant shapes giving 0% hits. Use grok-build's cache-aligned side-call trick for cheap classification ("should this thread unfold?") or recaps against the warm main prefix. Add a test that the cache key reaches the wire, and log cache read/write rates per call type.

**Async, delegation, re-entry**
7. **Type every injected message** (grok-build `SyntheticReason`). Distinguish human, steer/interjection, subagent-completed, scheduler-fired, notification-drain, runtime-context, and compaction-meta. Use the type to decide what is pruned, what collapses into a thread, what starts a turn, and what is replayed in a rebuild. Unknown types fail safe as turn boundaries.
8. **Batch async results and settle them in one successor turn** (OpenClaw settlement batch, grok-build idle-gated `NotificationDrain`). Never wake once per child event, and never let individual completions race each other into competing continuations. Coalesce thread activity into compact notices.
9. **A Focus Window completion = result + stats + handle.** Put a concise result (or a concrete blocker; reject empty or `NO_REPLY`) into the main channel. The full transcript stays in the harness's own store and is reachable through a paged `focus_history` tool (OpenClaw `sessions_history`). Do *not* ship summary-only completions (DimAgent): store the harness session id and path at spawn so the transcript is always one call away. Allow a silent private review turn: not every completion needs a user-facing message.
10. **Focus Windows get a scoped brief, not the main context.** Fresh by default, fork only on explicit need. Inject only the project instructions, never the persona (OpenClaw line 202; dots "only what the dot passes along"). The dots scope-violation data (8.6% → 19.7% with 5 → 10 intervening tasks) is the quantitative argument for keeping detail *out* of the main channel, which is Ducter's thread-collapse thesis.
11. **Steering semantics.** A user message during main-AI work is appended after the current tool batch. Unstarted sequential calls get a synthetic "skipped" result, so the respond-first property holds even mid-turn (OpenClaw queue-steering). "Pause main" ≠ "stop delegations" ≠ "cancel schedules" (dots controls).
12. **Treat a completed run as unverified.** The main AI checks the deliverable before reporting done (dots: "A completed run doesn't by itself confirm ...").

**Loops, waits, memory, UX**
13. **Have four separate primitives with separate ledgers.** (a) self-wake into the same session at T (OpenClaw `at` → `session:<key>`, dots self-pause/wake); (b) recurring schedule with explicit what/when/notify-threshold/destination fields (dots Scheduled); (c) event monitor that must be explicitly created; (d) standing intent ("when X appears, do Y"). Waits longer than the cache TTL should be *yield + wake*, not a blocking `wait` (DimAgent #16).
14. **Unattended approvals expire** (Grok Bot: ~30 min). Approvals in a live chat wait. Re-surface expired ones as a thread.
15. **Post-rebuild state rehydration** (grok-build compaction_context). After any cut-point rebuild, inject a live-state ledger: running Focus Windows, pending approvals, scheduled wakes, open threads, the active human ask. OpenClaw keeps "a bounded copy of the active human request" across compactions.
16. **Memory layers.** Persona and user files (immutable within an epoch); agent notes ("not a transcript", decisions updated in place); episodic channel log, searchable; background consolidation triggered *on rebuild or compaction* (Letta) rather than on a timer, so it piggybacks on the moment the prefix is being rewritten anyway. Memory is advisory: recheck live data for consequential decisions (Grok Bot).
17. **Route updates by type** (dots): progress, decisions, and urgent items go to different surfaces. Push only at milestones or when approval is needed (Muse). Keep durable outputs (reports, trackers) as artifacts outside the stream (Muse Spaces): that is another way to keep the main channel slim.
18. **Explicitly NOT do:** a raw single rolling session as the *only* mechanism (OpenClaw, DimAgent); memory-in-system-prompt recompiles (Letta); summary-only delegation results (DimAgent); per-event wake-ups; blocking waits past the TTL; image or tool-result rewriting while the cache is warm; letting page or tool content act as instructions (Grok Bot rule: only the user's messages are instructions).
