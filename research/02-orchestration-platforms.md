# 02 — How orchestration platforms build their core agent and wrap other harnesses

Researched 2026-11-08. Sources are cloned shallow repos (read-only, not executed) under
`<scratch>` (written `R/` below), plus official docs.
**V** = verified from source or official docs. **I** = inferred.

| Target | What it is | Source available? |
|---|---|---|
| **Multica** | Issue tracker where agents are teammates. Go server, local Go daemon, 28 harness backends | Yes, `multica-ai/multica` (R/multica) |
| **Raft** (Botiverse, formerly "Slock") | Slack-like workspace: agents are persistent peers in channels and threads | Yes, source-available FSL-1.1 release mirror `botiverse/raft-source` (R/raft-source). Also `botiverse/oar` (Open Agent Runtime) and `botiverse/raft-external-agents` |

## 1. Multica (R/multica)

**Driving harnesses (V).** Everything goes through one Go interface: `Backend.Execute(ctx, prompt, ExecOptions) (*Session, error)` (`server/pkg/agent/agent.go:18`). The package comment says it "mirrors the happy-cli AgentBackend pattern". There is one file per harness. `launchHeaders` (`agent.go:~560`) shows the transport for each:
- `claude (stream-json)`: `--output-format stream-json --input-format stream-json --verbose --permission-mode bypassPermissions`, plus `--resume <id>`, `--mcp-config`, `--strict-mcp-config`, `--settings <task-local file>`, `--effort` and `--max-turns` (`claude.go:1164-1216`). Daemon-owned flags are blocked from user `custom_args` (`claude.go:1148`).
- `codex app-server` (JSON-RPC). `pi (json mode)`. `dsh --profile multica (stdio)` uses a versioned JSONL protocol (`dsh.go:20-30`, "DSH owns the agent loop, session store, model catalog, tools, and MCP clients"). The ACP group covers hermes, kimi, kiro, qoder, devin, grok and traecli (`acp_session.go`). `opencode run (json)`. `cursor-agent (stream-json)`.
- Normalization: everything is reduced to 7 `MessageType`s (text, thinking, tool-use, tool-result, status, error, log) plus one terminal `Result{Status, Output, SessionID, Usage map[model]TokenUsage, ResumeRejected, ResumeRejectedTransient}` (`agent.go:234-340`). `TokenUsage` keeps input, output, cache-read and cache-write counts mutually exclusive.

**Mid-run steering (V), the most reusable idea in this repo.** `Session.Supplement(ctx, text)` and `SupplementReady()` (`agent.go:189`) are implemented per harness:
- Codex: the `turn/steer` RPC with `expectedTurnId` (`codex.go:1938-1952`).
- Claude: Claude has no "inject user input mid-turn" primitive, so the daemon registers SDK **control-protocol hooks** over stdin (`control_request subtype:initialize hooks:{UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, Stop}`). Pending text then goes into `hookSpecificOutput.additionalContext` at the next hook boundary. At `Stop`, it returns `{decision:"block", reason:text}` so the loop continues (`claude_supplement.go:21-215`). The daemon ignores hook callbacks from subagents (`agent_id`/`parent_tool_use_id` set). Durable supplements are claimed only after the provider confirms a live turn (`internal/daemon/task_supplement.go`).

**Resume (V).** The server stores `PriorSessionID` per (agent, issue) (`internal/daemon/types.go:121`). Every backend has to classify a failed resume. *Permanent* means the transcript is gone, the account is wrong, or the history can't be replayed: start a fresh session. *Transient* means use a fresh session this turn but keep the pointer. Network and quota errors keep the pointer so a retry can resume. `ResumeContinuityNotice` is text the caller supplies and the backend prepends when it unexpectedly lands on a fresh thread, so the agent knows its context is gone. The ACP resume-rejection classifier (`acp_session.go:13-80`) is a long record of real harness error strings.

**Orchestrator (V).** There is no custom loop. "Mika", the built-in Chief-of-Staff agent (`internal/service/builtin_agents/mika/INSTRUCTIONS.md`), is an ordinary agent on a harness. It routes work by calling the `multica` CLI (issue, agent, squad and autopilot commands), and its rules say chat is for intent, issues are for work, and "never edit code in a chat turn". **Squads** have a leader agent. Leadership is a per-task role that comes from an injected `## Squad Operating Protocol` briefing (`internal/handler/squad_briefing.go:34`): delegate by @mention comment, "be terse, members already read the issue", and record `multica squad activity <outcome>` on every trigger. **What the orchestrator sees** is the shared issue (comments and status). There are no transcripts. Coordination happens through a shared artifact, not by passing messages between sessions.

**Machines (V).** A local daemon (`multica daemon start`) probes installed CLIs, registers "runtimes" per workspace, and claims tasks over an authenticated WebSocket (`tasks.claim` RPC, up to 32 tasks per response, `internal/daemon/wakeup.go:22-35`). It can autostart through launchd or systemd user units, and it follows binary upgrades without interrupting a running task. `pkg/awakeclock` keeps host sleep from counting as agent silence in the idle watchdog (`idle_watchdog_suspend_test.go`). `internal/cloudruntime` forwards "fleet node" creation (for example `instance_type: g5.xlarge`) to a cloud API (I: managed cloud runtimes).

**Waiting (V).** `WakeupCondition` (`internal/service/issue_wakeup_condition.go:21-56`) is a structured predicate **the platform evaluates, not the LLM**. Types are `issue_field`, `children_done(stage)`, `pull_request{checks_finished|merged|conflicts}` and `other_issue{done|ended|in_review|blocked}`. The poll interval is 30s, and same-issue field changes are also pushed as events. Autopilots cover cron and events. Closing an issue disables its wakeups.

**Injection (V).** The runtime brief is written as a per-task CLAUDE.md, AGENTS.md or QWEN.md in the workdir rather than a system prompt (`agent.go:33-41`). MCP configs from the runtime and the agent are merged locally so secrets never leave the machine (`runtime_mcp.go`). A Remote MCP broker and a **plugin-hook MCP** turn HTTP plugin hooks into MCP tools, and calls go back through the server, which holds the signing secret (`plugin_hook_mcp.go`). Skills are written per task.

**Clever:** the Supplement abstraction, positive-evidence resume rejection, the awake-clock watchdog, and platform-evaluated wake conditions. **Avoid:** about 110k lines of Go in `pkg/agent`, mostly per-harness quirk handling (Cursor background-process lifecycle, Pi cleanup per OS). Supporting 28 harnesses this deeply is a maintenance tax. Ducter should support 3–4 well.

## 2. Raft / Botiverse (R/raft-source, R/oar, R/raft-external-agents)

**Model (V, docs.raft.build).** A server holds channels, DMs, threads and tasks. Agents are persistent members with their own identity, a `MEMORY.md` plus `notes/` on their computer, and search over all Raft messages. An agent wakes on a message in a joined channel, a DM, an @mention, a reply in a followed thread, or a self-set **reminder**. Otherwise it is idle and spends nothing. "Reset Session & Restart" keeps notes, "Full Reset" wipes the workspace. There is **no privileged main AI**: every agent is a peer. "Cindy" is an onboarding agent (`daemon/src/cindy.ts`).

**Driving harnesses (V).** A daemon ("Raft Computer") per machine spawns runtimes. Supported runtimes are Claude Code, Codex, Cursor, Grok, Kimi, OpenCode, and a built-in Pi bundled with the daemon. Claude is launched as a persistent process with `--output-format stream-json --input-format stream-json --include-partial-messages --append-system-prompt-file <standing prompt> --disallowed-tools … --setting-sources project,local --resume <id> --mcp-config <managed>` (`packages/daemon/src/drivers/claudeLaunch.ts:102-131`). Codex runs through `app-server` with `turn/start` or `turn/steer` (`drivers/codex.ts:975,1367`). Each driver declares an explicit **capability descriptor** (`drivers/types.ts:14-40, 355-385`):
```
lifecycle: persistent{stdin: direct|notification, inFlightWake: queue|steer}
         | per_turn{start: immediate|defer_until_concrete_message, exit, inFlightWake: spawn_new|coalesce_into_pending}
input: {initial, idle: stdin|request|sdk_prompt, busy: stdin_steer|request|sdk_steer|unsupported}
turnBoundary: parsed_event|sdk_event|process_exit;  postTurn: keep_alive|close_stdin|terminate_process
session.recovery: fresh|resume_or_fresh;  communication.chat: "slock_cli"
```
Agents speak only through the bundled `raft` CLI (`chat: "slock_cli"`, `drivers/raftCliGuide.ts`). Chat is not the model's text output. Each driver has its own event normalizer (`claudeEventNormalizer.ts`, `codexEventNormalizer.ts` and others). OAR (`botiverse/oar`) is their published "programming interface for all agent harnesses". The daemon loads it one runtime at a time (`oarLoader.ts`).

**Expire-aware resume (V). This is Ducter's thesis, already shipped.** In `daemon/src/wakeSessionRecycle.ts` (RFC 070), when an agent wakes after the prompt cache is certainly cold (**idle > 60 min, matching the 1h cache TTL measured across the fleet**) *and* the last request's context was over **128k tokens** (input + cache_read + cache_creation, read from the tail of the Claude transcript JSONL), the daemon *does not* `--resume`. It starts a fresh session seeded with a constructed panel instead (`decideWakeRecycle`, line 230). Their notes say cost is insensitive to the threshold anywhere in 48k–256k. Unknown facts always mean resume. Findings recorded in the code:
- The v1 briefing ("your session was retired… consult MEMORY.md first") made **13/13** canary sessions open with state-rebuilding rituals. v2 is **intentionally empty** (line 267). The fresh input contains only ambient XML blocks (memory, recent messages, in-flight facts) followed by the ordinary wake prompt, "as a chat window never announces its context was rebuilt".
- The v3 panel (`wakeBriefingPanel.ts`) uses the retired transcript as an *action log* and never replays it verbatim. It re-reads files from the world and labels stale content with when it was observed. Old "Next step:" lines are reduced to bare pointers because a 10k panel gives stale agenda items false salience. It is evaluated by behavioral equivalence with real full-context continuations (1,301 samples).
- `startupMemoryBlock.ts`: the head of MEMORY.md is injected only into *fresh* sessions. Resumed ones skip it to avoid duplicating content in the cached prefix.
- A cold-idle sweep runs every 10 min (`COLD_IDLE_SWEEP_MS`, line 308).

**External agents (V).** `raft-external-agents` is a Claude Code **channels plugin** (`claude --channels plugin:raft-channel@raft`). A bridge sends a metadata-only `POST /wake` on loopback with a per-session token and a debounce window, and the model pulls message bodies itself with `slock message check`. A wake proves "injected", not "processed". Delivery and read cursors are owned server-side.

**Machines (V).** `raft-computer setup /<slug>` enrolls a machine with a device login. Laptop agents stop when the laptop sleeps, and their messages queue and catch up on reconnect. Cloud servers stay on. "Move to another computer" transfers the workspace and memory but starts a new conversation (`agentMigration*.ts`). A credential proxy keeps provider credentials brokered by the daemon (`agentCredentialProxy.ts`). Related: `botiverse/antiproton`, a "durable multi-tenant runtime… credentials never enter the model's context".

**Clever:** the capability descriptor, cache-TTL-aware recycling with measured thresholds, the empty briefing, a CLI instead of chat-as-output, and doorbell-style wakes. **Avoid:** the peer-only model has no persona owner. Delivery ledgers and residency invariants (`agentNoProcessResidency.ts`, I1–I5) show how much state machinery a distributed inbox needs.

## 3. Lody (R/lodyai-lody)

**Driving harnesses (V).** It is **ACP-only**. Each harness is an ACP adapter process: `apps/cli/src/{claude,codex,deepseek,devin,grok}-acp-entry.ts`, with adapters in `LodyAI/acp-extension-*`. Claude and Codex are forks of Zed's `claude-code-acp` and `codex-acp` (V via GitHub repo descriptions; I: the Claude adapter uses the Claude Agent SDK, as upstream does). Kimi, Pi, OMP and DSH have their own adapters. Normalization is ACP's session/update model. Capabilities such as modes and config options come from ACP advertisement and are cached (`specs/acp-capability-*.md`). State syncs through Loro CRDT streams (`packages/loro-streams-rpc`) and supports E2EE workspaces.

**Orchestrator (V, `specs/session-orchestration.md`).** **Any session can orchestrate**. There is no dedicated super agent. Every child gets the built-in Lody MCP server with tools such as `lody_session_create[_many]`, `lody_session_chat[_many]`, `lody_session_status_many`, `lody_session_history`, `lody_session_queue`, `lody_operation_*`, `lody_machine_list`, `lody_schedule_*` and `lody_automation`. Design rules:
- The causal delegation depth is capped at 16 (`CHAIN_DEPTH_EXCEEDED`). B may not open a new chat back to the sender driving its turn (`REVERSE_CHAT_FORBIDDEN`).
- Chatting to a busy session **steers** it when the agent supports that, otherwise the message is queued. The receipt is `steered|queued|dispatched`. An uncertain steer is never replayed (`STEER_DELIVERY_UNKNOWN`), and the requesting agent decides whether to resend.
- The coordinator sees **identity, not content**. List and status return title, PRs, branch, turn start, last output time, current action, queued inputs, and `lastTurnFailure{reason: usage_limit|context_overflow|model_error|permission_denied|cancelled|agent_crash|unknown, resetAt}`. Full history is available only by explicit paged `lody_session_history(maxChars, since, role)`.
- Agent-authored input carries a provenance header saying it is not human input. A relayed human instruction can cite the original message, which Lody verifies against history ("quoted authority", no delegation tokens).
- `lody_machine_list` reports quota and reset times, so a coordinator can stop dispatching to an exhausted config.

**Waiting (V).** `lody_automation` registers a **durable JavaScript condition** that the host keeps checking after the agent exits or the daemon restarts (`apps/cli/src/mcp/automation-tools.ts:10-18`). "CodeMode" gives the condition scoped `ctx` reads, bounded HTTP, and local commands. It returns false or a resume result, and a matched result commits together with its continuation id. A PR/CI poller and quota-recovery wakes (resume when quota resets) are built in (`apps/cli/src/automations/AGENTS.md`).

**Session ops (V).** DSH fork is supported at turn boundaries through ACP fork plus `forkAtTurn`, copying a native event prefix with no model call (`specs/deepseek-harness-session-fork.md`). There are worktree lifecycle specs, and the ACP idle timeout is 30 min (changelog 2026-04-13). `lody daemon start` on any machine runs as a background daemon with automatic restart.

**Clever:** orchestration as an MCP tool surface available to *every* harness, steer/queue receipts, failure reason codes, and durable condition code. **Avoid:** with no single owner of the user relationship, sessions can cross-chat. They needed hop limits and reverse-chat bans to stop loops.

## 4. DeepSeek Harness and dsh-superagent

**dsh itself (V, R/deepseek-harness/docs).** Cordis plugin kernel. Profiles include `web`, `headless`, `sdk` and `acp`. The session is an **append-only `SessionEvent` log**, and "model-visible means logged": every model request can be rebuilt from the log (`docs/architecture.md:124-130`). Fork, resume and transcripts all derive from it, and forking at a turn boundary uses `ctx.agents.create({seed, inheritedEventCount})`. The loop has a per-session **inbox** with `agent/inbox/inserted|spliced|claimed` events (`docs/agent-lifecycle.md`). Prompt modes are `queue | steer | inject`. Compaction is a plugin (`dsh-compaction-basic`) triggered from pre-step pressure or context overflow. Subagent providers sit behind one seam, "from a fresh child agent to a delegated turn in another product" (`docs/subsystems/subagent.md`). External executions are supported but refuse follow-ups.

**dsh-superagent (V, R/dsh-superagent-prototype/docs).** This is the closest public analogue to Ducter's main-AI design. A research prototype released 2026-10-31 alongside the article *Exploring Super-agent Design*:
- **Philosophy:** "take as little human attention as possible". The agent acts only when asked or when a written rule allows it, speaks only when a person must act or can use a result, and asks one structured question at a time.
- **Domain:** Source → Trigger → Thread → Eval (a deterministic gate plus model assessment) → Ticket with an immutable Mandate → Assignment → Executor. Subscriptions fan messages out from a Thread to Tickets. A person's message on a subscribed thread goes **straight to the worker, bypassing the router** (`docs/001-domain.md`).
- **Main Session = one long-lived DSH session** (`orchestrator`, preset `dsh-superagent-router`) with 14 tools: `orchestrator_route` (1–20 decisions per call), `_eval`, `_ticket_note`, `_reply` and others (`docs/007-architecture.md` "Main Session tools"). **What it sees:** candidate cards, `follow_up` notices, `worker_report` (ticket card + state + **summary ≤600 chars** + read pointer), and `worker_attention` (a question). These are **steered into its running turn** (`src/app/sessions.ts:104`, `prompt(masterId, …, 'steer')`). Notices like `ticket_ended` are injected without waking it. Paged read resources (`ticket/<id>/transcript`, 4k-char pages) exist for drill-down.
- **No-wait guard:** the router may not call `sleep`, shell timeouts over 30s, or job waits over 5s. "Reports and job results arrive automatically… end the turn when nothing is left to do" (`prompts/orchestrator.md`, `sessions.ts` noWait).
- **Executor Session per Ticket** (`worker-<ticket id>`) with one directory per ticket, prepared by a user `prepare` command (typically `git worktree`, 10-min cap). Foreground shell commands move to background jobs after 5s so the worker can take new messages at the next step. A job finishing wakes the worker. Background work gets 30 min after a turn, then is killed. There are concurrency slots, plus **one reserved slot for a human message** (`docs/003-execution.md`).
- **Recovery:** effects are stored first and done afterwards (outbox), with backoff of 2s doubling to 60s. On restart, assignments resume with a recovery note: "check directory, git history and GitHub before repeating any outside action". The record of which inputs each session actually read survives restarts. Ticket state is independent of DSH session state, so a ticket can be handed to a new executor.
- **Waiting:** "a condition that needs waiting is an ordinary Source". Eval never schedules its own delayed triggers. GitHub and Feishu Sources poll subscribed threads for two weeks after the last activity.
- Reported result (article, via press): p95 completion time went from 29.5 to 15.7 min versus a single session, on synthetic workloads.

## 5. herdr (R/herdr)

**Driving harnesses (V).** It **owns PTYs; it does not wrap harnesses.** A server and client pair keeps terminals alive across detach and SSH drop (Rust, vendored `ghostty-vt`). State detection is **screen scraping with versioned per-agent TOML manifests**: regex rules over regions such as `osc_title`, `bottom_non_empty_lines(12)` and `last_non_empty_above_prompt_box`, with priorities, mapping to `working | blocked | idle | done | unknown` (`src/detect/manifests/claude.toml`). The Claude spinner glyph is matched per CLI version, and manifests update independently of the binary (`manifest_update.rs`).
- Optional **hook integration**: herdr installs a `SessionStart` hook into Claude, Codex and Pi configs (`src/integration/assets/claude/herdr-agent-state.sh`, `claude_settings.rs` with format-preserving JSON edits). The hook calls `herdr pane report-agent-session <pane> --agent-session-id … --agent-session-path …`. After a restart herdr restores the layout and types the agent's own resume command into the shell (`src/agent_resume.rs`).
- **Agent-facing control:** a skill (`skills/herdr/SKILL.md`) plus a JSON CLI and socket API let agents spawn panes, `agent start`, send prompts, read output, and `wait` for output regex or agent state (`src/api/wait.rs`). It is gated on `HERDR_ENV=1`. Remote machines use an SSH stdio bridge (`src/remote/host.rs`, `attach.rs`).
- **Orchestrator:** none built in. Any agent can drive others through the CLI. The model sees raw pane output.
- **Avoid:** scraping breaks with every TUI release (note the per-version glyph comments), and "unknown" is a common state. It suits a *human* cockpit, not a typed event bus. **Clever:** the hook-reported session id makes resume cheap and lets it work with any harness.

## 6. Conductor (docs only; closed source)

- **V (docs):** Mac app. Bundles Claude Code, Codex and OpenCode, or uses the system binary. Cursor goes through the Cursor API. Each chat tab is one harness and one model. Each workspace is a **git worktree** with its own branch, 10 ports (`CONDUCTOR_PORT..+9`), and env vars (`CONDUCTOR_WORKSPACE_{NAME,ID,PATH}`, `CONDUCTOR_ROOT_PATH`, `CONDUCTOR_IS_LOCAL`). `conductor.json` (newer: `.conductor/settings.toml`) defines `setup`, `run` and `archive` scripts plus `runScriptMode`. **Checkpoints:** before each agent response, Conductor snapshots the working branch to a private git ref. Reverting deletes the later messages and code, and the agent loses that knowledge. **Cloud** (launched 2026-07-30) runs on **Vercel Sandbox** microVMs with an API for creating workspaces, sending prompts and reading replies. Cloud agents get a `RunLocalCommand` tool that reaches back to the user's Mac, and a `DiffComment` tool for review. There is no CLI or API for local workspaces. Sources: conductor.build/docs/reference/{harnesses,checkpoints}, `/.well-known/agent-skills/conductor/SKILL.md`, the Vercel case study, and wotai.co/blog/conductor-joins-meta.
- **Unknown:** whether Conductor drives Claude through the Agent SDK or the CLI, and Codex through app-server. No public source says. **I:** Conductor bundles binaries and uses the user's own login, which is consistent with spawning the CLI/SDK subprocess (Claude) and app-server (Codex).
- **Lesson:** its value was the *workspace layer* (worktree, scripts, ports, checkpoint refs, diff review). That layer is commodity and easy to rebuild. Being closed source left users stranded at shutdown, which argues for Ducter being open with local state.

|---|---|---|---|---|---|

| Codex transport | app-server JSON-RPC | app-server | ACP (codex-acp) | n/a | PTY |

## Implications for Ducter

1. **Use the same shape as Raft's adapter capability descriptor.** Declare per harness: lifecycle (persistent or per-turn), idle and busy input mode (`stdin_steer | request | sdk_steer | unsupported`), turn boundary, post-turn behavior, and recovery. Normalize events to a small set (Multica's 7 message types + `Result{status, sessionId, usage incl. cacheRead/cacheWrite, resumeRejected{permanent|transient}}`). Start with Claude (stream-json or Agent SDK), Codex (app-server), Pi (json/RPC) and DSH (stdio or ACP). Keep ACP as the generic fallback, not the primary path, because native transports expose more: steer, cache usage, compaction events.
2. **Steering needs harness-specific mechanics.** For Claude, use Multica's trick: SDK control-protocol hooks, with `additionalContext` at tool boundaries and `decision:block` at Stop. Ignore callbacks from subagents. For Codex, use `turn/steer` with `expectedTurnId`. Always return a Lody-style receipt (`steered | queued | dispatched | unknown`), and never auto-replay an uncertain steer.
3. **Expire-aware resume is validated, so reuse the numbers and the lessons.** Use a 1h cold gap (matching the cache TTL) and a context threshold around 128k, computed from transcript tail usage. Unknown facts mean resume. On recycle, send **no "you were reset" announcement**. Provide ambient blocks (memory head, recent thread slice, in-flight facts re-read from the world) and then the real message. Inject memory only into fresh sessions, so it never duplicates content in a cached prefix. Apply the same rule to Ducter's main AI over its infinite channel: the channel is the durable state, and the physical session is disposable.
4. **Main AI design: follow dsh-superagent's router discipline, but give it a persona.** One long-lived main session. Focus Window reports arrive as *bounded* cards (about 600 chars + read pointer) steered into its turn, with full transcripts reachable through paged read tools. Low-value notices are injected without waking it. A **no-wait guard** forbids sleep and polling in the main loop, so every wait becomes a durable condition. Human follow-ups in a Focus Window's thread go straight to that window, and the main AI is only notified. Reserve one concurrency slot for human messages.
5. **Waiting belongs to the platform, not the LLM.** Use structured conditions (Multica: PR checks finished/merged, children done, field changes) and escape-hatch code conditions (Lody's durable JS that returns false or a resume result), evaluated by a durable scheduler (a CF Durable Object alarm fits). Fire by waking the owning thread with a compact event, Raft-style, so the model pulls details itself.
6. **Expose platform control to child harnesses as one tool surface.** Use either an MCP server (Lody) or a CLI with a skill (Multica, Raft, herdr). CLI plus skill is cheaper in tokens and works in any harness. MCP gives typed schemas. Either way, add provenance headers on agent-authored input, a hop limit, and no reverse chat to the sender, from day one.
7. **Persistence:** keep Ducter's own append-only event log as truth ("model-visible means logged", from dsh). Keep harness session ids as *cache pointers* with permanent and transient rejection semantics, plus a continuity notice when the main AI lands on a fresh session. Store side effects first and do them afterwards (an outbox). On restart, send a recovery note: "check git, PR and channel before repeating any outside action".
8. **Machines:** a per-machine daemon with an outbound WebSocket claim (Multica, Raft), launchd or systemd autostart, and an *awake clock* so laptop sleep never looks like a hung agent. Queue messages while a machine is offline, and wake a sleeping Linux box only for real work (I: Wake-on-LAN or cloud start). Keep credentials brokered by the daemon (Raft credential proxy, Multica plugin-hook MCP) so secrets never reach the model or the cloud.
9. **Avoid:** screen scraping as the primary signal (herdr's per-version regexes), supporting dozens of harnesses deeply (Multica's 110k-line backend), peer-only designs without an owner of the user relationship (Raft, Lody needed loop guards), and closed workspace layers (Conductor's shutdown). Rebuild Conductor's useful bits cheaply: worktree per Focus Window, setup/run/archive scripts, port blocks, and a per-turn checkpoint ref.
